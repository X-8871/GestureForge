# HarmonyConnect 安路赛题二 → XC7Z020CLG400-2 综合复刻评估报告

评估日期：2026-09-08（南京时间，UTC+8）  
目标器件：xc7z020clg400-2  
性质：根据功能描述、器件文档和条件假设进行的工程可行性评估；不是已完成移植的验收报告。

## 1. 直接结论：能够复刻多少

**从芯片能力看，参考报告列出的功能没有发现必然超出 XC7Z020 能力的项目。在具备合适 DDR、千兆以太网、摄像头、显示接口、第二块 FPGA 和模型资料的前提下，11 个编号项目都可以作为复刻目标。但目前不能承诺全部性能指标、准确率和原作品内部实现完全一致。**

这里的“11 项可作为目标”是条件式可行性判断，不是成功概率、完成比例或交付保证。第 10 项本身是性能指标，必须与其余功能分开验收。

| 复刻口径 | 能达到的程度 | 不能混淆的边界 |
|---|---|---|
| 用户可见功能 | 控灯、图片收发、视频采集传输显示、分类、目标切换和断线恢复，均有明确实现路径 | 实现路径存在，不代表当前已经在板上验证 |
| 单块板、具备所需外设 | 10 项实际功能中，8 项可在单板系统实现；第 5 项双 FPGA 通信、第 8 项主辅 FPGA 分工只能替代或待补第二板；第 10 项性能另计 | 单板内两个模块、两个 IP 地址或 PC 模拟节点，都不是两块实体 FPGA |
| 两块合适的 FPGA 板及完整外设 | 10 项实际功能均有完整复刻路径；第 10 项性能需测试 | 第二块板无需必须为 XC7Z020，但必须有足够资源与兼容接口 |
| 原模型、原协议、原画面效果逐项一致 | 当前资料不足，无法确认 | 需要网络结构、权重、量化参数、预处理、协议和测试条件 |
| 80% 准确率、5.46 ms、180+ FPS、30 FPS、240 Mbps 同时复现 | 当前不能保证 | 准确率、核心延迟、吞吐、端到端帧率和网络流量是不同指标 |

**不能诚实地说“因为我的 coding 能力不够，有哪几项绝对做不了”。现有证据无法得出这种结论；同样，也不能说“所有代码我都能一次写对”。最难、最依赖反复验证的是定点 CNN、MIPI 接入以及多时钟视频/DDR/网络整机调度。**

## 3. 芯片资源是否够

### 3.1 XC7Z020 可用资源

| 资源 | 器件规模 |
|---|---:|
| LUT | 53,200 |
| 触发器 | 106,400 |
| BRAM | 140 个 36 Kbit 块，合计 5,160,960 bit |
| DSP | 220 个 DSP48E1 |
| 处理器 | 双核 ARM Cortex-A9 |
| 外设控制能力 | PS 提供以太网、SD 等控制器，仍需要板上 PHY、卡座和实际连接 |

数据来自 [AMD DS190](https://www.amd.com/content/dam/xilinx/support/documents/data_sheets/ds190-Zynq-7000-Overview.pdf)。BRAM 算术容量约 630 KiB，含块的校验位组织；普通 32-bit 数据配置等情况下有效数据容量更低，不能把 630 KiB 全部当通用帧缓存。CLG400 是封装，-2 是速度等级，不能据此指定整机时钟或视频帧率。

DSP48E1 的乘法器为 25×18 bit，需按 INT8 的符号扩展、流水线和累加规则使用；这里不假设一个 DSP 天然实现多路独立 INT8 MAC。[AMD DSP48E1 原语文档](https://docs.amd.com/r/2025.1-English/ug953-vivado-7series-libraries/DSP48E1?contentId=Oc~qLt2fDjVcZqEpM_Z9jA)

### 3.2 原 CNN 资源与目标器件的数量级比较

| 原报告自述 | 与 XC7Z020 的粗略比较 | 能说明什么 |
|---|---|---|
| 约 9K LUT | 约为目标 LUT 数量的 16.9% | 有余量的初步迹象；不同厂商 LUT 和映射不可逐个等同 |
| 约 7K FF | 数量比约 6.6% | 不代表移植后一定只占这个比例 |
| 约 26 DSP | 数量比约 11.8% | DSP 数量没有明显硬性不足 |
| 40 M9K + 12 M32K | 按 9×1024 和 32×1024 bit 估算为 761,856 bit，约 93 KiB | 仅按容量相当于 20.7 个 BRAM36，即向上取整 21 块；端口/宽深/碎片会增大实际占用 |
| 23,210 个 INT8 参数 | 单权重数据约 22.7 KiB，185,680 bit | 权重本体不大；偏置、量化系数和激活另算 |

上述比例均为本报告算术估算，不是 Vivado 综合结果。BRAM 容量等效值不等于可以把所有权重和激活紧凑塞进 21 块。M9K/M32K 的具体组织也应由原工程资料核实。

**工程推断：小型 CNN 与基本视频链路值得优先尝试单芯片集成；不能将原作品“UDP 与 CNN 占用超过 80%”直接套用到 XC7Z020。**

### 3.3 真正需要 DDR 的地方

640×480 RGB888 一帧为 921,600 byte，约 900 KiB，已经大于全芯片 BRAM 的算术容量。即使没有 CNN，也无法完整放入一帧这种格式。

方法只有明确的取舍：完整视频缓存使用外部 DDR；或者改为低分辨率/低位宽/行缓存流式处理，但后者不能提供相同的完整帧重组和缓冲能力。DDR 帧缓存可经 AXI VDMA 接入。[AMD AXI VDMA 概述](https://docs.amd.com/r/en-US/pg020_axi_vdma/Overview)

## 4. 逐功能复刻方案：每项两种方法

以下“可完整复刻”均指满足列出的硬件与资料条件后的功能目标，不表示已验证。

### 1）PC 通过 UDP 控制 LED 和数码管

**判断：可完整复刻；编码难度较低，算力资源不是瓶颈。**

- **方法 A，推荐：PS 网络控制。** PC 上位机发送带命令号和序号的 UDP 包；PS 用 GEM 和 lwIP 收包，通过 GPIO 或 AXI-Lite 控制 LED/数码管。PL 实现动态扫描、亮度控制和按键消抖。
- **方法 B：PL 网络控制。** 在 PHY 确实接到 PL 时，自写或集成 MAC、ARP、IPv4、UDP，命令解析后直接驱动外设。控制路径更独立，但协议与 PHY 时序工作更多。

硬件限制：缺少可控 LED 或数码管需加模块；PS MIO 上的 PHY 不能仅靠 XDC 改接成 PL 外设。编码风险：大小端、重复命令和数码管扫描极性。  
验收：连续控制、重复包、非法长度、目标错误测试；LED/数码管结果与命令一致。

### 2）PC 发送 RGB888 图片，FPGA HDMI 显示

**判断：可完整复刻；依赖 DDR 与可用显示输出。**

- **方法 A，推荐：PS 重组、PL 显示。** PC 将图片转为 RGB888；以帧号、包序号、偏移和长度分包。PS 写 DDR 后确认整帧完整，在显示帧边界交换缓存；PL 经 VDMA 读取并生成显示时序。
- **方法 B：PL 重组与写存储器。** PL UDP 解析器直接将图片有效负载经 AXI 写入 DDR，用包位图检查完整性，再交给 HDMI。适合减少 CPU 拷贝，代价是 AXI 突发、反压和缓存管理更复杂。

硬件限制：无 HDMI 输出电路不能靠代码产生可接显示器的物理接口；外接发射器或合适扩展板可补齐。编码风险：RGB 顺序、跨包像素、撕裂和 Cache/DMA 一致性。  
验收：传输后帧数据校验一致，色条正确，乱序/丢包时不显示混合帧。

### 3）从 SD 卡读取图片并发到 PC／另一 FPGA

**判断：可完整复刻；静态图像对带宽要求较宽松。**

- **方法 A，推荐：PS SD + 文件系统。** 通过板载 SD 控制器和 FatFs/操作系统读取 BMP 或原始 RGB 文件，转换到统一帧格式，再经 UDP 发送。PC 或另一块板运行相同接收协议。
- **方法 B：PL SD 控制器。** 外接接到 PL 的 SD 模组，编写 SPI 或原生 SD 块读控制器；先采用已知扇区位置的原始图片布局，避免把文件系统作为前置难点。固定扇区布局不等同于支持任意 FAT 文件。

硬件限制：SD 若接 PS MIO，不能直接由普通 PL 引脚驱动。编码风险：文件格式、扇区边界和错误恢复。  
验收：不同尺寸图片端到端字节校验；缺卡、读失败不使系统挂死。原报告主要验证读取，不能据系统组成描述推断其已完整演示 SD 写入功能。

### 4）OV5640 采集视频并通过 UDP 发到 PC

**判断：可完整复刻功能；原分辨率与帧率暂不能承诺。**

- **方法 A，优先低风险接入：DVP 模组。** SCCB 配置 OV5640，用 PCLK、VSYNC、HREF 和并行数据采集，异步 FIFO 跨时钟，进行像素格式整理，写 DDR 后发送。需要匹配的 DVP 模组、引脚和电平。
- **方法 B：MIPI CSI-2 模组。** 按底板电路使用适配的 D-PHY 接收方案和 CSI-2 接收逻辑，解析数据类型、行帧包和像素排列，再接共同的视频处理链。选定接收 IP 前核查 Zynq-7000、引脚、电气与授权支持。

硬件限制：DVP 与 MIPI 不能仅换连接器名称就兼容。摄像头模式、网络链路和 DDR 决定帧率上限。编码风险：摄像头寄存器时序、CDC、像素对齐、队列溢出；MIPI 路线风险更高。  
验收：先固定低分辨率稳定采集，再检查实际帧数、丢帧计数、长时间运行和 PC 显示延迟。

### 5）双 FPGA 通过 UDP 通信

**判断：有第二块 FPGA 可完整复刻；只有一块板不能完整复刻实体拓扑。**

- **方法 A，推荐：两块板统一应用协议。** 两端分别运行图片/视频收发和控制程序，经千兆交换机连接，角色通过配置选择；两块板可以是不同芯片平台。
- **方法 B：两块板使用 PL UDP 数据通路。** 两端 PHY 接 PL 时，硬件完成分包收包与图像链路，适合证明 FPGA 网络数据通路；调试复杂度高于 PS 网络方案。

硬件限制：缺第二块板是系统硬件缺件，不是 XC7Z020 LUT 不够，也不是代码写不出来。PC 模拟可用于调试，但不能算双 FPGA 验收。  
验收：两块实际设备之间传图、视频和结果回传，分别重启后可恢复。

### 6）按键切换 UDP 目标，一主多从

**判断：可完整复刻；多从同时发送需要额外带宽核算。**

- **方法 A，推荐：目标表切换。** 按键消抖后更新 PS 的目标 IP/端口，解析 ARP，完成准备后从下一完整帧切换；新会话带独立编号，接收端清理旧帧。
- **方法 B：PL 目标表。** 用寄存器表保存目标 IP、MAC、端口及有效状态，由硬件帧边界状态机选择目的地。适合 PL UDP 架构。

硬件限制：第二目标若要求 FPGA，需第二块板；向多个设备逐一单播相同视频，发送带宽随副本数增加。“切换目标”不能自动等同于“同时无限多路”。编码风险：ARP 过期、切换发生在半帧、不同接收端速率不一致。  
验收：切换后新目标从完整帧开始接收，旧目标不再收到后续单播视频。

### 7）网络断线后恢复传输

**判断：可完整复刻演示效果；恢复时间需定义并实测。**

- **方法 A，推荐：PS 状态机。** 检测 PHY 链路变化，停止发送并释放过期帧；重连后确认速率、恢复网络接口和目标解析，重新建立帧会话。只有 DMA 异常时才执行相应复位。
- **方法 B：PL 恢复控制。** MDIO 轮询 PHY，链路状态触发 MAC/FIFO/组帧状态更新，链路稳定并完成 ARP 后，从新帧恢复。

硬件限制：PHY、交换机自动协商有实际耗时，代码不能保证插线瞬间恢复。编码风险：描述符泄漏、半包残留、失效 MAC 和重连后 DMA 不再启动。  
验收：反复拔插、接收端重启和交换机断电测试；报告恢复时间分布。UDP 本身不提供重传或断点续传；静态图片可增加请求重发，实时视频一般丢旧帧追最新帧。

### 8）主 FPGA 采集、辅 FPGA CNN 识别及结果返回

**判断：双板可完整复刻；单板可以实现相同业务闭环，但属于架构替代。**

- **方法 A，忠实复刻：双板分工。** 主板采集并发送图像；辅板接收后完成预处理和 PL CNN，返回帧号、类别、分数、耗时。主板/PC 把识别结果关联到对应帧。
- **方法 B，推荐单板阶段：本地 CNN。** XC7Z020 的 PL 同时承担采集和 CNN，经 DDR 或流接口共享图像，PS 负责网络与控制。PC 接收视频和分类结果。此法减少板间传输，但不满足“双板执行”要求。

硬件限制：实体双板与双显示器需要相应设备；单板并发占用需要综合确认。编码风险：结果与画面错位、预处理不一致、任务队列积压。  
验收：以帧号检查推理结果对应关系，同时统计核心计算时间和端到端延迟。

### 9）纯 Verilog INT8 CNN 汽车十分类

**判断：可设计同类硬件 CNN；原模型的准确率与输出不能根据当前描述恢复。**

- **方法 A，原模型可获得时推荐：移植数学行为。** 获取完整网络、权重、偏置和量化规则，写 Python 整数黄金模型，再用 Verilog 实现深度可分离卷积、逐点卷积、激活、池化和分类控制；把安路专用存储器/乘法资源换成 Xilinx 推断或原语实现。
- **方法 B，原模型缺失时：重新训练同任务模型。** 在合法可用的十类汽车数据上训练轻量 CNN，采用 INT8 量化并导出确定的整数规则，再写通用可复用的串并行 MAC 阵列和层调度器。可复刻“硬件十分类”功能，但模型及准确率属于新结果。

硬件限制：激活尺寸和 MAC 数比参数量更影响性能；23,210 个参数不能推出推理所需运算量。编码风险最高：有符号计算、零点、舍入、饱和、累加溢出、padding、depthwise 索引、BN 折叠和逐通道缩放。

我可以编写上述模型、RTL 和验证代码，但不能在没有数据和测试的情况下保证 80% 准确率，也不能保证第一版 RTL 数值正确。  
验收：每层整数结果与黄金模型对齐；独立测试集测准确率和混淆矩阵，明确训练/验证/测试划分，最后做摄像头域的测试。“画面里汽车位置定位”不是十分类本身包含的功能。

### 10）5.46 ms、180+ FPS 与整机约 30 FPS

**判断：可以制定追赶指标的实现方案，现阶段无法承诺数值复现。此项是性能验收，不是额外业务功能。**

- **方法 A，先正确再优化：资源复用。** 从较低并行度和稳妥时钟开始，实测每层周期与访存停顿；在瓶颈卷积层增加并行 MAC、优化布局和权重访问，逐步减少延迟。
- **方法 B，吞吐优先：分层流水与缓存重叠。** 为热点层分配独立计算单元，乒乓激活缓存，使采集、传输和计算重叠。代价是 BRAM、DSP、布线和调试压力上升。

5.46 ms 的倒数约为 183.15 次/秒，仅在单次连续执行等假设下可估计吞吐；流水化设计的延迟和启动间隔应分别报告。50 MHz 下 5.46 ms 对应约 273,000 个周期，但不能据此推出网络 MAC 数。

对于每图需要 M 次 MAC、P 路每周期各完成一次 MAC、频率 f 的理想实现，计算时间下界为 M/(P×f)；实际还需考虑利用率、访存和控制气泡。M 未知，不能用资源倍数许诺性能倍数。

硬件限制：计算并行度、BRAM 端口、DDR/网络/摄像头吞吐。编码风险：综合映射、时序收敛、任务并发效率；写法低效也会造成性能问题，不能全部归咎硬件。  
验收：同一模型、输入尺寸、时钟、数据路径下报告核心延迟、启动间隔、持续吞吐、端到端帧率及资源/时序报告。

### 11）RGB888 → YUV420 → RGB888

**判断：可完整复刻转换与传输功能；无法复原已经丢弃的色度细节。**

- **方法 A，推荐：PL 流水线。** 定点矩阵完成 RGB 到 YCbCr（常用“YUV”称呼），对 2×2 像素块低通/平均后抽取色度，存为明确的 I420 或 NV12 格式；接收端插值上采样再转回 RGB。
- **方法 B：PS 软件转换。** ARM 端实现同一矩阵和采样规则，可用整数/NEON 优化；先用于小分辨率验证，与 PL 逐像素比较，再测其是否满足整机目标。

8-bit RGB888 为 24 bit/像素，8-bit 4:2:0 平均为 12 bit/像素，所以未计封装的像素数据量减半。这是有损色度抽样，不是 H.264/H.265，也不是数学无损。[Linux YUV420 格式文档](https://www.kernel.org/doc/html/v4.10/media/uapi/v4l/pixfmt-yuv420.html)

硬件限制：PS 转换可能受 CPU 和存储带宽限制；PL 需要行缓存。编码风险：BT.601/BT.709 矩阵、全范围/有限范围、UV 顺序和采样位置不一致。  
验收：用色条、细字、彩色边缘和自然图像与软件参考比较，测误差/PSNR，并确认像素负载缩小约 50%；不能要求往返像素全部一致。

## 5. 哪些属于编码问题，哪些属于硬件问题

| 问题或现象 | 正确归因 | 可行处理 |
|---|---|---|
| 包解析错误、花屏、跨帧混合、结果帧号不对 | 编码/系统设计缺陷 | 修复状态机、协议、缓存所有权与测试 |
| INT8 模型软件正确而 RTL 输出错误 | 编码/量化实现缺陷 | 逐层逐值定位，不能说芯片算不准 |
| DSP 很空闲却推理很慢 | 可能是调度、访存或代码结构；需测量 | 性能计数器定位后再优化 |
| 综合或布局后占满资源 | 可能是设计过度展开，也可能是目标过大 | 先复用/流水/重新分配，再判断器件是否不足 |
| 没有第二块 FPGA、摄像头或数码管 | 外部硬件缺件 | 补设备；软件模拟只能部分替代 |
| PHY/SD 只接 PS MIO，却要求 PL 直接驱动 | 板级连线约束 | 用 PS 外设，或增加接到 PL 的模块 |
| 无 DDR 却要求完整 VGA RGB888 帧缓存 | 硬件存储容量约束 | 加可用存储、降低规格或改流处理 |
| 单千兆口传未压缩 1080p60 YUV420 | 网络物理带宽不足 | 降帧/降分辨率或改更强编码/更快链路 |
| YUV420 往返无法还原全部 RGB 像素 | 抽样的信息损失 | 若需无损，保留全色度或另选真正无损编码 |
| 重新训练达不到原称 80% | 数据、模型、训练和评测共同影响 | 补资料、固定测试条件后诊断；不是单看 FPGA |
| 无板卡接入、无波形或错误日志 | 验证条件不足 | 提供 JTAG/UART/ILA 或现场测试反馈 |
| 缺原模型/协议，无法逐位复现 | 资料不足 | 获取原资料，或明确采用新模型/新协议 |

2. CNN 定点一致性、自写 CSI-2 接收、HDMI 高速输出、RGMII 时序和多路 DMA 并发，是最容易写错且必须靠仿真、综合及上板反馈修正的部分。我不能把“能生成代码”表述为“已证明可稳定运行”。

## 6. 视频带宽与存储预算

以下为本报告计算，均是紧密存放、8-bit 分量的纯像素数据，未计 UDP/IP/以太网封装和包间隙。MB 使用十进制。

| 分辨率与帧率 | RGB888 单帧 | RGB888 负载 | YUV420 单帧 | YUV420 负载 |
|---|---:|---:|---:|---:|
| 640×480 @30 FPS | 0.9216 MB | 221.184 Mbps | 0.4608 MB | 110.592 Mbps |
| 640×480 @60 FPS | 0.9216 MB | 442.368 Mbps | 0.4608 MB | 221.184 Mbps |
| 1280×720 @30 FPS | 2.7648 MB | 663.552 Mbps | 1.3824 MB | 331.776 Mbps |
| 1280×720 @60 FPS | 2.7648 MB | 1,327.104 Mbps | 1.3824 MB | 663.552 Mbps |
| 1920×1080 @30 FPS | 6.2208 MB | 1,492.992 Mbps | 3.1104 MB | 746.496 Mbps |
| 1920×1080 @60 FPS | 6.2208 MB | 2,985.984 Mbps | 3.1104 MB | 1,492.992 Mbps |

计算公式：RGB 带宽 = 宽×高×帧率×24；YUV420 带宽 = 宽×高×帧率×12。

- 百兆口不能持续承载表中的任何一条纯像素视频流，即便 VGA30 YUV420 也超过 100 Mbps。
- 千兆口无法承载超过 1,000 Mbps 的条目；低于 1,000 Mbps 也不保证实际软件链路达到。
- 1080p30 YUV420 的 746.496 Mbps 只是链路容量上有可能，需要测 PS/DMA、包处理和并发负载。建议先把 VGA30 作为集成起点。
- 若“64 帧”指 64 FPS，则 VGA YUV420 负载为 235.9296 Mbps，与原报告约 240 Mbps 接近，但这仅是可能解释，不能反推原视频尺寸或格式。
- 显示器输出 1080p60 可以重复显示较低帧率输入，并不要求网络一定传 60 张新帧。

RGB888 双缓冲容量：VGA 为 1.8432 MB，720p 为 5.5296 MB，1080p 为 12.4416 MB，另需摄像头/网络队列与 CNN 缓存。

DDR 预算按实际读写次数计算，不能只看摄像头输入。例如 VGA30 RGB888 每遍读或写为 27.648 MB/s；采集写入、HDMI 读取和网络读取三遍即至少 82.944 MB/s，还未算预处理、CPU 拷贝和仲裁损耗。双缓冲解决并发覆盖，不能消除持续带宽不足。

## 7. 建议架构与关键决策

### 7.1 默认实施路线

```text
OV5640 ─→ PL 采集/格式整理 ─→ AXI DMA/VDMA ─→ PS DDR
                                              ├─→ PL HDMI 输出
                                              ├─→ 缩放/归一化 ─→ PL INT8 CNN
                                              └─→ PS UDP ─→ PC/第二 FPGA
SD 卡 ─→ PS 文件读取 ──────────────────────────┘

PC 控制 ─→ PS UDP ─→ 寄存器/GPIO ─→ LED/数码管/目标选择
CNN 结果 ─→ 帧号关联 ─→ PS UDP/画面叠加
```

网络优先使用 PS 的 GEM，CNN 的乘加与层计算放 PL。这样仍是硬件 CNN，不应宣称整个系统“全纯 Verilog”。PS 的网口经 MIO 可接外部 PHY，EMIO 则提供 GMII 给 PL 适配；这不能把已接到 MIO 的物理网线自动重接给自写 MAC。[AMD MIO 说明](https://docs.amd.com/r/en-US/ug585-zynq-7000-SoC-TRM/Gigabit-Ethernet-Controller-using-MIO)、[AMD EMIO 说明](https://docs.amd.com/r/en-US/ug585-zynq-7000-SoC-TRM/Gigabit-Ethernet-Controller-using-EMIO)

### 7.2 决策记录（评估建议，待具体板卡核对后实施）

| 决策 | 原因 | 代价或切换条件 |
|---|---|---|
| ADR-01：优先 PS 网络 + PL 视频/CNN | 利用现有硬外设，集中资源做图像和推理 | PS 数据搬运需优化；只有明确要求 PL UDP 且硬件连接允许时换路线 |
| ADR-02：视频整帧放 DDR，BRAM 放权重/行缓存/热点激活 | 全帧容量超过片内 RAM | 必须管理 DMA、Cache、总线带宽和帧所有权 |
| ADR-03：先验证原模型是否可得 | 避免把新训练结果冒充原模型复现 | 无原模型则采用重新训练分支，80% 不作为预先承诺 |
| ADR-04：单板先完成业务闭环，再接双板 | 降低同时调试采集、推理和网络的复杂度 | 最终双 FPGA 演示仍需第二实体节点 |
| ADR-05：视频与静态图片使用不同丢包策略 | 视频重视新鲜度，图片重视完整性 | 协议实现要区分业务类型 |

网络仅部署在可控局域网；输入长度、尺寸、偏移和包数必须检查上限，避免越界和资源耗尽。对视频采用有界队列并记录丢帧；重要状态变化和错误需要可观察计数器，而非只凭“画面还在动”判断系统正常。

### 7.3 如果实际板卡确实为 AX7Z020

ALINX 对应手册描述了 1GB DDR3、千兆网口、HDMI、SD 和 MIPI 摄像头接口，且其核心板说明将以太网和 SD 列为 PS 端接口。这使 PS 网络/SD 与 PL 视频/CNN 的方案更自然；仍需对应你的实际 PCB 版本核对。[ALINX 厂家手册](https://github.com/alinxalinx/AX7Z020B_2023.1/blob/master/RSTdocxs/7Z020UserManual_CN/AX7Z020UserManual.rst)

不能将这份手册的接口直接认定为你当前板卡的配置，也不能因为摄像头同叫 OV5640 就认定 DVP 模组可插入 MIPI 接口。

## 8. “所有代码都由我编写”的范围

| 范围 | 可承担内容 | 对结论的影响 |
|---|---|---|
| 项目代码全部编写，使用基础工具/IP/库 | PC 上位机、PS 应用、RTL、训练/量化/导出脚本、黄金模型、仿真、XDC、工程脚本 | 本报告默认；工作量可集中在项目功能和验证 |
| CNN 全手写 Verilog | 算子、存储布局、层控制、定点缩放与输出；可推断 BRAM/DSP | 能对应原作品“纯 Verilog CNN”的要求 |
| 不用 HLS，但允许基础 DMA/时钟 IP | 手写核心 RTL，基础设施用成熟 IP | 推荐的折中，不影响 CNN 是手写 RTL |
| 连 MAC、DMA、SD 文件系统也从零编写 | 都可形成独立实现任务 | 工作量和错误风险显著增加，不带来必然更好的效果 |
| 所有链路必须 PL、完全不用 PS | 需要 PHY/SD/存储实际可被 PL 使用 | 对 PS MIO/DDR 固定连线的板卡可能不成立；是架构与硬件约束 |
| 完全不依赖任何现成代码或工具 | 无法按字面满足常规 FPGA 工程 | 至少仍依赖综合工具、器件定义与硬件原语，需明确排除范围 |

以上不把 CPU 推理或 HLS 自动生成的 RTL 当作“手写纯 Verilog CNN”的等价验收。

每阶段交付相应源码、复现脚本、输入样例、日志和报告。综合通过不等于时序通过，时序通过不等于上板功能通过。准确率必须来自测试，不能来自 RTL 仿真推断。

## 10. 最终判断

**现在不应因为担心 XC7Z020 的 LUT 或 DSP 不够而放弃该项目。更合理的路径是：保留 XC7Z020，确认板上接口，采用 PS 网络/SD + PL 视频/手写 INT8 CNN + DDR 帧缓存，先完成单板业务闭环，再补双板拓扑。**

- **功能层面：** 10 项实际功能都有实现路径，第 10 项性能作为独立目标验收。
- **单板边界：** 双 FPGA 通信和双 FPGA 分工不能被单板内部模块严格替代。
- **硬件硬限制：** 缺外设、错误电气接口、固定 MIO 连线、片内帧存储容量和链路线速。
- **编码与工程难点：** 定点 CNN、MIPI/高速接口、CDC、DDR/网络并发、错误恢复和时序收敛。
- **资料限制：** 原模型、权重、数据划分和测量口径未提供，不能承诺原准确率及性能。
- **本次完成内容：** 文档评估与资源/带宽计算；未编写移植代码，未执行综合、实现或上板测试。
