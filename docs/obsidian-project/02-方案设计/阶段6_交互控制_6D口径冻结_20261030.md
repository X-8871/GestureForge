## 2. 口径冻结（一）：业务状态映射

生产者/消费者统一使用下列映射，**优先级自上而下**（高优先级命中即停）：

| 优先级 | 条件 | 业务状态 | 交互含义 |
|---|---|---|---|
| 1 | `status.valid == 0` | **ERROR** | 本帧无有效结果（生产者未发布/解析失败），交互层不得沿用旧结果做动作 |
| 2 | `status.overrun == 1` | **ERROR** | 生产者内部丢帧/不一致，本帧结果不可信 |
| 3 | `status.stale == 1` 或 `age_publish > 200 ms` | **TIMEOUT** | 结果过期，交互层保持上一稳定状态、不触发新动作 |
| 4 | `status.valid == 1 && n_dets == 0` | **NO_HAND** | 本帧已处理但无手，交互层进入"无手"分支（可用于撤销/回中） |
| 5 | 其他（`valid==1 && n_dets>0`） | **OK** | 正常结果，按检测项驱动交互 |

- `age_publish = (GT_now − result_time) × 1000 / 333,333,343`（`result_time` 定义见 §3）
- **200 ms 门限不变**（沿用 6-A/6-D 已批准口径）；显示侧"超 1 帧 stale"与 `47.3 s + 16.7 ms` 年龄仅用于显示语义，**不替代**交互 200 ms 门限

## 3. 口径冻结（二）：`session_id` / `result_seq` / 可信 `result_time`（不改冻结 32 B ABI）

**扩展方式：sidecar（旁挂区），不触碰 32 B 头与 16 B 项布局。**

- 位置：结果块基址 `0x20800000` **+0x100**（0x20 头 + 14×16 项 = 0x100，即紧接第 13 号项之后；**第 14/15 号检测项因此不可用**，检测项上限 **14**）
- 结构 `S5X1`（32 B，小端）：

| 偏移 | 字段 | 类型 | 语义 |
|---|---|---|---|
| +0x00 | `magic2` | u32 | `0x53355831`（"S5X1"） |
| +0x04 | `version` | u32 | `1` |
| +0x08 | `session_id` | u32 | 每次 POR/新会话 +1（见下） |
| +0x0C | `result_seq` | u32 | 会话内结果发布序号，严格 +1，回绕按 §3.2 |
| +0x10 | `result_time_lo` | u32 | **发布完成时刻** GT ticks 低 32 位 |
| +0x14 | `result_time_hi` | u32 | 高 32 位 |
| +0x18 | `seqlock` | u32 | 偶=稳定、奇=写入中（见 §3.3） |
| +0x1C | `reserved` | u32 | 0 |

**3.1 `session_id` 生成规则（冻结）**
- 上电后首次发布前读 GT 初值：`session_id = (GT_at_start >> 10) & 0xFFFF`，并对仍可读的旧 sidecar 做最多 8 次碰撞递增
- **主张范围（rev4 收窄）**：仅主张「**同一会话内 `session_id` 恒定**」；**跨 POR 唯一性不主张**（GT 在 POR 后重启、旧 DDR sidecar 无持久保证，×8 碰撞重试也可能耗尽）。跨 POR 唯一需 NVRAM/序列号方案，列为阶段7 前置（R-14）
- 会话内 `session_id` 不变；`result_seq` 从 0 起严格 +1

**3.2 `result_seq` 回绕/重启规则（冻结，与 6-A B25 一致）**
- 回绕阈值 `0xFFFFFFFE`：**无特殊停发语义**，`0xFFFFFFFE → 0xFFFFFFFF` 正常递增
- `0xFFFFFFFF → 0` **一律拒绝**（须新 `session_id`）；同会话内任何**回退**一律拒绝并置 `status.overrun=1`
- 新 `session_id` 时 `result_seq` 从 0 重计，旧会话结果不得被消费者继续使用（消费者见 `session_id` 变化即丢弃旧状态）

**3.3 原子发布协议（seqlock，rev4 顺序修正）**

> rev4 修正（2026-10-31 01:2x，依据 Codex C4 独立复审 `3f6efbf4…`）：原顺序有两个真实缺陷 —— ① 写者未在写 payload 前把「奇数锁」发布到内存可见；② 消费者首次取锁前未 invalidate。以下为**必须实现**的顺序。

**写者（生产者）**
1. `seqlock++`（变奇）→ **单独 cache clean/flush 该 4 B 锁行** → `__DSB()`；
2. 写 32 B 头 + 检测项（≤14）+ sidecar 非时间字段 → **最后写 `result_time`**；
3. **clean/flush payload 区间 `[0x20800000, 0x20800120)`（288 B）** → `__DSB()`；
4. `seqlock++`（变偶）→ **clean/flush 锁行** → `__DSB()`。

**消费者**
1. **先 invalidate**（锁行 + payload 区间）；
2. 读 `seqlock`（记为 `s1`）；若为奇 ⇒ 重试（≤3 次）；
3. 读 payload（头/项/sidecar）→ `__DMB()`；
4. 再读 `seqlock`（`s2`）；要求 `s1 == s2` 且为偶，否则重试（≤3 次，超限判 TIMEOUT）；
5. 只有 1–4 全通过才算一致快照；**「只读一次锁」或「先取锁后 invalidate」均不符合本协议**。

**3.4 可信 `result_time` 定义（冻结）**
- **`result_time` = 结果块"发布完成"时刻的 GT 读数**：生产者把 `result_time` 写在整块最后一个字段（含 sidecar），紧接着 `flush`；消费者读到 `result_time` 即认为该结果已发布
- 与显示 ABI 的 `inf`（模拟推理完成）区别：`inf` 仅表示"推理完成"，`result_time` 表示"**已发布且可被消费**"；交互 `age_publish` 用 `result_time`
