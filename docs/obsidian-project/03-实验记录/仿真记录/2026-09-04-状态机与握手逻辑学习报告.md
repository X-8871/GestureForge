## 三、开始学习时不会或容易混淆的内容

### 1. 不清楚 `state` 和 `next_state` 的区别

开始时容易把下面两句话理解成同一件事：

```systemverilog
state <= next_state;
next_state = state;
```

后来理解为：

- `state` 是当前状态，保存在触发器中；
- `next_state` 是根据当前输入计算出来的下一状态；
- `always_ff` 在时钟上升沿把 `next_state` 保存到 `state`；
- `always_comb` 默认让 `next_state` 保持为当前的 `state`。

状态机的基本数据流是：

```text
当前 state + 输入信号
          ↓
    always_comb
          ↓
      next_state
          ↓ 等待时钟上升沿
        state
```

### 2. 担心 `always_comb` 中没有覆盖所有条件会产生锁存器

例如：

```systemverilog
IDLE: begin
    if (start)
        next_state = PROCESS;
end
```

这里当 `start=0` 时，代码没有再次给 `next_state` 赋值，看起来像是会产生锁存器。

后来理解了，只要在 `case` 之前写默认赋值：

```systemverilog
always_comb begin
    next_state = state;
    // 后面根据条件覆盖 next_state
end
```

即使 `start=0`，`next_state` 也已经有默认值 `state`，所以不会产生锁存器。

### 3. 不清楚什么时候必须写 `begin/end`

开始时认为每个 `if` 后面都必须写 `begin/end`。后来明确：

- 只有一条语句时，可以省略；
- 有多条语句时，必须使用；
- 复杂嵌套时，建议使用，避免 `else` 配对错误。

例如，下面是合法的：

```systemverilog
if (rst)
    count <= '0;
else
    count <= count + 1'b1;
```

### 4. 不理解 `COUNT_WIDTH` 和 `$clog2`

开始时把“处理周期数”和“计数器位数”混在了一起。后来理解：

- `PROCESS_CYCLES` 表示需要处理多少个时钟周期；
- `COUNT_WIDTH` 表示计数器需要多少位；
- `$clog2(N)` 计算至少需要多少位二进制表示 `N` 种状态；
- `logic [COUNT_WIDTH-1:0] count` 才是根据需要自动调整位宽。

例如：

```systemverilog
localparam int COUNT_WIDTH =
    (PROCESS_CYCLES <= 1) ? 1 : $clog2(PROCESS_CYCLES);

logic [COUNT_WIDTH-1:0] count;
```

当 `PROCESS_CYCLES=3` 时：

```text
COUNT_WIDTH = $clog2(3) = 2
count       = logic [1:0]
```

### 5. 不知道 `busy` 和 `done` 如何由状态产生

后来理解它们是当前状态的组合译码：

```systemverilog
assign busy = (state == PROCESS);
assign done = (state == DONE);
```

因此：

- 处于 `PROCESS` 时，`busy=1`；
- 处于 `DONE` 时，`done=1`；
- 处于 `IDLE` 时，二者都为 `0`。

## 四、今天学习的核心知识

### 1. 三状态 FSM 的职责

| 状态 | 含义 | `busy` | `done` |
|---|---|---:|---:|
| `IDLE` | 等待启动 | 0 | 0 |
| `PROCESS` | 正在处理 | 1 | 0 |
| `DONE` | 处理刚刚完成 | 0 | 1 |

状态转移关系：

```text
IDLE --start--> PROCESS
PROCESS --计数完成--> DONE
DONE --一个时钟周期后--> IDLE
```

处理期间再次出现 `start` 时，状态机仍然保持 `PROCESS`，不会重新启动。

### 2. `always_ff` 和 `always_comb` 的分工

时序逻辑保存状态和计数器：

```systemverilog
always_ff @(posedge clk) begin
    if (rst)
        state <= IDLE;
    else
        state <= next_state;
end
```

组合逻辑计算下一状态：

```systemverilog
always_comb begin
    next_state = state;

    case (state)
        IDLE: begin
            if (start)
                next_state = PROCESS;
        end

        PROCESS: begin
            if (count == PROCESS_CYCLES - 1)
                next_state = DONE;
        end

        DONE: begin
            next_state = IDLE;
        end

        default: begin
            next_state = IDLE;
        end
    endcase
end
```

`always_comb` 会在仿真开始时执行，并且在它读取的信号发生变化时重新执行，例如 `state`、`start` 或 `count` 变化时。

### 3. 计数周期的计算

计数从 `0` 开始时，`PROCESS_CYCLES=3` 的计数过程为：

```text
0 → 1 → 2 → DONE
```

因此判断条件写成：

```systemverilog
count == PROCESS_CYCLES - 1
```

而不是直接等于 `PROCESS_CYCLES`，否则容易多运行一个周期。

### 4. 同步复位导致的初始 `X`

当前代码中的复位写在：

```systemverilog
always_ff @(posedge clk)
```

因此它是同步复位。仿真时间 0 到第一个时钟上升沿之间，`state` 尚未执行复位，`busy` 和 `done` 暂时显示 `X` 是正常现象。经过复位有效的时钟上升沿后，状态回到 `IDLE`，输出变为确定值。

## 五、编写过程中发现的问题与修正

### 问题 1：重复定义 `PROCESS_CYCLES`

错误思路是同时写：

```systemverilog
parameter int PROCESS_CYCLES = 3;
logic [2:0] PROCESS_CYCLES = 3;
```

同一个名字被定义了两次。修正方式是保留参数，把运行中的变量命名为 `count`。

### 问题 2：计数器只声明，没有更新

仅写：

```systemverilog
logic [1:0] count;
```

不会让计数器自动增加。必须在 `always_ff` 中明确写清零和加一逻辑。

### 问题 3：`busy` 和 `done` 没有驱动

只声明输出并不会自动产生信号，必须用连续赋值或组合逻辑给出定义：

```systemverilog
assign busy = (state == PROCESS);
assign done = (state == DONE);
```

### 问题 4：分号和 `begin/end` 配对错误

曾经出现过：

```systemverilog
count <= '0
```

正确写法是：

```systemverilog
count <= '0;
```

并且内层 `if` 在 `else` 前必须先关闭：

```systemverilog
if (count == PROCESS_CYCLES - 1) begin
    count <= '0;
end else begin
    count <= count + 1'b1;
end
```

### 问题 5：计数器位宽写法不够节省

```systemverilog
logic [PROCESS_CYCLES-1:0] count;
```

当 `PROCESS_CYCLES=3` 时，这会产生 3 位计数器。虽然可以运行，但它表示“位数等于周期数”，不是最小所需位数。使用 `COUNT_WIDTH` 可以根据参数自动选择位宽。

## 六、测试平台与波形验证

测试平台在 `D:\FPGA_Competition\sim\tb_control_fsm.sv` 中完成，覆盖了：

1. 复位后输出回到空闲状态；
2. `start` 能触发一次处理任务；
3. `busy` 在处理期间有效；
4. `PROCESS` 状态期间再次 `start` 不会打断当前任务；
5. 处理完成后 `done` 只保持一个时钟周期；
6. `DONE` 之后返回 `IDLE`。

从 Vivado 2026.1 波形截图可以观察到：

```text
复位阶段       → busy=0，done=0
第一次 start    → busy 拉高
处理期间再次 start → busy 继续保持，未提前产生 done
处理完成        → busy 拉低，done 拉高一个周期
完成后          → done 拉低，回到 IDLE
```

波形开始时 `busy` 和 `done` 的短暂 `X` 对应同步复位尚未遇到第一个时钟上升沿，属于预期现象。

## 八、仍需巩固或待验证的内容

1. 当前设计默认 `start` 是一个时钟周期的脉冲。如果 `start` 一直保持高电平，状态机每次回到 `IDLE` 后可能再次启动，需要后续加入边沿检测或明确接口协议。
2. `PROCESS_CYCLES` 应限制为大于等于 1，参数为 0 时不具有合理意义。
3. 目前只完成行为仿真，还没有完成综合、时序分析、比特流生成和上板验证。
4. `state` 和 `count` 目前是模块内部信号，后续可以根据调试需要决定是否增加可观测输出或使用 Vivado 层次信号观察。
