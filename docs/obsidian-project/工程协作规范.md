# AX7Z020 项目工程协作规范

版本：1.0。生效日期：2026-09-10（UTC+8）。用户已批准保存并长期使用。

本文件是协作流程的唯一维护正文。[[总控]] 保存项目稳定事实与规范入口，[[项目进程]] 是当前状态的唯一来源，[[项目接手提示词]] 提供角色入口。规则变更不等于工程功能完成。

## 1. 目标与原则

优先保证流程可靠、职责清楚、输入输出明确、版本可追溯、验收有证据、失败可恢复、新窗口可接手；在此前提下减少重复操作。

- AI 承担设计、编码、自动验证和记录整理；Wong 确认关键需求、实物条件，执行物理操作并提供真实观察。
- 未执行的检查标为未执行。仿真通过、审查通过、上板通过分别记录。
- 不得为了通过而自行降低验收标准。资料、旧提示词和历史方案不是当前批准需求。
- 已能使用工具执行的检查由 AI 执行；工具不可用时记录限制并提供操作单。
- 文本使用 UTF-8，时间使用 UTC+8，代码注释与文档字符串使用中文。
- 2026-09-10 起工程实施不再要求 Wong 先独立编码；历史学习记录保持原样。必要原理理解服务于验证和答辩。

## 3. 窗口与人员职责

同一个 Codex 项目使用 `D:\FPGA_Competition`，不复制三个相同项目。

| 角色 | 输入 | 职责 | 输出 |
|---|---|---|---|
| 总控窗口 | 需求、计划、当前状态与证据 | 拆任务、管理依赖和变更、组织验收 | 任务卡、验收结论、状态与下一步 |
| 开发窗口 | 已明确任务卡与基线 | 设计、编码、测试、修复和交付 | 指定版本、设计更新、证据、操作单 |
| 审查窗口 | 任务卡、固定版本、差异与证据 | 独立检查需求、实现、测试及证据 | 问题清单与复核结论 |
| Wong | 关键待确认项与操作单 | 确认需求及实物条件，执行物理操作 | 真实结果、日志、照片或视频 |

命名示例：`总控｜AX7Z020 B方案`、`开发｜S2-T03 INT8乘加模块`、`审查｜S2-T03 INT8乘加模块`。

- 总控长期维护。开发与审查按可独立验收目标创建；同一任务修复留在原窗口。
- 实现代码只有一个写入方。审查不直接修改被审实现，可在隔离位置验证。
- 审查固定提交，修复后指定新版本；共享文件和板卡操作不得并发冲突。
- 新窗口读取规则、状态和任务记录，不能依赖其他聊天的记忆。
- 验收与交接齐全后归档。上下文过长时先保存版本、结论、问题及下一步再换窗口。
- 创建、转发、归档自动化依赖工具及授权，不默认存在后台自动协作。
- AI 审查不能代替独立参考结果、自动检查和实物验证。

## 4. 任务卡与输入要求

按可独立验收的结果拆任务，不按文件数量拆分。总控生成任务卡：

| 字段 | 必填内容 |
|---|---|
| 编号与目标 | 名称、目标、边界 |
| 前置条件 | 依赖模块、硬件、工具和基线 |
| 输入输出 | 数据格式、位宽、符号、时序、复位和异常行为 |
| 验收标准 | 方法、阈值、正确性依据和证据 |
| 修改范围 | 模块、配置与文档 |
| 交付要求 | 源码、配置、产物和说明 |
| 未知项 | 解决情况、阻碍与可继续工作 |

常规实现选择由 AI 记录并推进。实物电气条件、关键接口语义、范围与指标、重大架构、数据标签和评估口径存在实质歧义时先核实；不受影响的工作继续。验收条件在实现前确定。

## 5. 状态与验收关口

状态：待定义 → 待开发 → 开发中 → 待审查 → 待人工验证或待验收 → 已验收。审查失败回开发修复；任何环节可受阻，记录原因与所需输入。

| 关口 | 通过条件 | 材料 |
|---|---|---|
| G0 任务就绪 | 目标、接口、依赖与标准足够明确 | 任务卡、基线、未知项 |
| G1 开发交付 | 实现完成，适用自动检查执行 | 差异、设计、结果、待审版本 |
| G2 审查通过 | 阻断问题关闭，证据充分 | 问题清单、处理结果、复核版本 |
| G3 实物验证 | 适用板上测试达到标准 | 操作单、原始结果、产物版本 |
| G4 任务验收 | 所有适用标准满足且版本一致 | 结论、证据索引、遗留问题 |
| G5 阶段验收 | 阶段与集成要求满足 | 阶段检查表、冻结版本、交接材料 |

不适用 G3 时注明理由。G2 不代表 G3 或 G4。规格或接口错误退回 G0，评估受影响任务。阻断问题不能延期后视为关闭。

## 6. 验证与证据

| 层次 | 判断内容 | 证据 |
|---|---|---|
| 参考计算 | 数值与算法正确性 | 固定样例、独立参考与比较日志 |
| RTL／软件测试 | 功能、边界、接口与复位 | 测试日志、断言、必要波形 |
| 构建与实现 | 可构建、约束、资源和时序 | 工具报告、约束及实现结果 |
| 板上验证 | 实物行为 | 串口、采集数据、照片或视频 |
| 系统验收 | 集成、性能、稳定性与恢复 | 统计数据、条件与异常测试 |

证据记录对象版本、工具配置、模型数据版本、方法、时间、预期、实际、阈值及原始文件位置。随机测试保留种子，统计明确样本数和口径。截图不替代原始日志。参考模型需要独立依据或手算样例，避免复刻同一错误。

每次修改做影响范围内回归，模块和阶段冻结做相应完整验收，不重复要求 Wong 执行已有工具证据的检查。混合版本资源数不能直接相加当成系统资源。工具或硬件不可用时保留未执行项。

## 7. 开发、审查与修复

1. 开发核对差异，完成适用验证，提交本轮相关代码。
2. 指定提交哈希、任务卡和证据入口供审查。
3. 审查问题写明位置、影响、依据与验证方法。
4. 开发修复或提供可复查的不同意见，执行回归并提交新版本。
5. 审查复核修复与受影响部分，通过后进入人工验证或验收。

问题分阻断、非阻断和可选建议。非阻断延期注明影响；可选建议不成为隐含验收门槛。同一问题连续两轮无实质进展，总控重新核查规格、环境和诊断方法。

仅提交本轮相关文件，不混入无关改动、密钥和缓存。提交失败报告原因，不能声称代码已完成提交。

## 8. 人工操作与反馈

操作单包含：前提与版本、板卡接线与工具、准确路径及逐步操作、预期与等待时间、异常停止点、需保存材料和恢复方法。不能只写“烧录后看是否正常”。

聊天突出：当前状态、需要执行的步骤、预期、回传内容和完整记录入口。详细设计与审查材料落文档。

Wong 反馈步骤、现象与附件；如换过文件、接线或设置则注明。已有任务信息由 AI 提取，版本不明时核实。正常结果也应按操作单保存必要原始证据。

## 9. 记录与变更

任务主记录包含任务卡、状态、设计链接、开发审查轮次、证据、人工结果、最终版本与验收结论。重大故障记录“现象—候选原因—区分实验—确认依据—修复—回归—适用边界”，必要时配图，不用聊天全文代替报告。

需求、接口或标准改变时，记录原因、内容、受影响任务与证据，以及是否重新审查、上板。范围、关键指标和重大架构由 Wong 确认；范围内常规修复自主推进。

## 10. 阶段冻结与交付

阶段验收检查：必需需求都有结论，同一系统版本集成通过，适用资源、时序、性能和稳定性达标，阻断问题清零，延期有说明，代码配置模型产物对应，接手说明可用，最近通过版本可恢复。

最终交付验证从干净环境或干净工程副本按文档重建，并完成约定板上检查。清单包含提交哈希、板卡工具版本、源码配置模型产物、构建运行步骤、验收证据、已知限制及恢复方法。阶段指标引用已确认任务与阶段计划，不在本规范重复维护数值。

## 11. Git 与知识库同步

远程为 https://github.com/X-8871/GestureForge ，当前分支为 `main`。工程源码在原路径直接跟踪，指定 Obsidian 项目在原位置编辑后单向同步到 `docs/obsidian-project/`。其他 Vault 内容与历史不导入。

同步不自动传播删除，不覆盖快照独立修改，不自动提交推送，无后台同步。远程笔记变更先协调后回写知识库。排除缓存与第三方参考视频；原文件不删除。远程失败保留本地提交并报告“未推送”，不能以本地提交代替远程成功。

## 12. 提示词、Skill 与规范维护

使用统一规则、三个角色短入口和任务卡。工作流 Skill 不是当前前置条件；先跑通真实任务，再根据重复遗漏、稳定自动步骤和跨项目复用需求决定。竞赛交付中的技能包要求与是否安装本地工作流 Skill 分别管理。

Skill 如加入，应引用本规范，不另写冲突正文。常规文字与路径纠错可按授权维护；范围、职责和验收规则实质变化需 Wong 审核。更新版本、日期和变更记录，保持入口链接一致。

## 13. 生效后的实施顺序

规范保存及入口更新 → 核实工具和板卡对应关系 → 选择真实任务 → 运行 G0—G4 → 依据实际问题修订 → 推广到后续阶段 → 决定 Skill 是否必要。此顺序不代表相关工程验证已完成。
