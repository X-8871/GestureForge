# 我的 AI 工程实验工作流

本文面向 Wong，说明实际怎样使用已经建立的流程；规则和验收条件引用 [[工程协作规范]]，不维护第二套规范。首次开工细节见 [[明日实验启动指南]]，以后每次从 [[项目进程]] 的当前任务接手。

## 1. 我的分工

我负责提出目标、确认关键需求及实物条件、执行必须由人完成的操作、提供真实观察，并理解结果用于答辩。AI 负责设计、编码、软件检查、诊断、记录和版本管理。没有证据时不让我签“通过”；我也不需要为验收重新编写 AI 已验证的代码。

## 2. 每次开始

1. 打开本项目 Obsidian 的 [[项目进程]]，看当前任务和阻碍。
2. Codex 使用工程目录 `D:\FPGA_Competition` 的同一个项目。
3. 有总控窗口就继续；新窗口首次使用 [[项目接手提示词#总控启动]]。
4. 告诉总控：`继续当前任务。先核对版本和交接记录，告诉我本次目标、验收条件以及需要我做什么。`
5. 由总控给出任务编号和主记录路径。目标有歧义时我确认；常规文件检查和实现细节由 AI 处理。

首次执行才检查 S0-T01/T02；以后依据实际状态继续，不能每天重新开始 S0。

## 3. 开发、审查和我的操作

| 时点 | 我做什么 | AI 必须交付什么 |
|---|---|---|
| 开发开始 | 新开发窗口首次贴开发提示词，附任务编号；已有任务继续原窗口 | G0 核对、设计/实现与测试 |
| 开发交付 | 把完整版本哈希、任务主记录路径交给审查窗口 | 待审提交、证据和未执行项 |
| 审查失败 | 给开发发送问题轮次与记录路径 | 修复提交、相关回归、问题回应 |
| 修复完成 | 给审查发送新哈希和轮次 | 复核结论及剩余阻断项 |
| 需要上板 | 只按开发提供的准确操作单接线/运行 | 前提、文件、步骤、预期、异常停止点和恢复方法 |
| 实物结果返回 | 回传步骤、现象、附件和配置变化 | 诊断及 G3 结果；不伪造现场观察 |
| 任务收尾 | 让总控核对关口与材料 | G4 结论、状态更新、提交和远程状态 |

开发和审查不同时修改同一工作区或主记录。审查期间开发暂停修改被审实现。一个模块的小修复继续原窗口，只有新的可独立验收目标才新开任务。

## 4. 我可以直接发送的短消息

```text
开发：执行任务〔编号〕，读取主记录〔完整路径〕，按现有验收条件推进。
审查：检查任务〔编号〕、提交〔完整哈希〕，读取主记录〔完整路径〕，记录结论和依据。
开发：处理审查第〔轮次〕的问题，不改变验收标准；修复后给出新提交和回归结果。
总控：核对任务〔编号〕所有适用关口，缺证据就保留未通过，更新当前状态。
```

任务编号、路径和哈希由 AI 提供，我只转交，不猜值。首条角色提示词仅新窗口使用一次；上下文丢失时补交接入口，不粘贴全部历史聊天。

## 5. 失败、暂停与恢复

- 失败：`第〔步骤〕步，实际现象〔描述〕，附件〔日志/图片〕，本轮是否换过接线/文件/设置〔说明〕。`
- 暂停：`保存交接：当前版本、最后成功步骤、未关闭问题、证据和下次动作。不要把未完成任务标为完成。`
- 恢复：`读取该任务交接区，先核对实际版本，再继续。`
- 同一问题两轮没有进展：让总控重查规格、环境和测试方法，不不断加新提示词碰运气。
- GitHub 不可用：允许保留本地提交，明确“未推送”；恢复后重试，不强推覆盖未知远程历史。
- 出现不认识的工作区改动：先核实来源，不能删掉或混入本任务提交。

上板后修改了实现、约束或参数，要重新经过相应测试和审查，再做受影响的实物复验；此前的上板证据不能证明新版本。

## 6. 文件保存与每日收尾

笔记编辑源：当前 Obsidian 项目。工程代码：`D:\FPGA_Competition`。原始证据：工程 `report/evidence/任务编号/运行编号/`。仓库 `docs/obsidian-project/` 是快照，不能作为第二个笔记编辑源。

每天结束由 AI 检查：任务记录已保存、真实状态已更新、相关文件已提交、远程是否成功、下次入口明确。Git 同步流程见 [[工程入口]]；没有后台自动同步，不能以为修改 Obsidian 后 GitHub 就立即更新。

任务通过且交接齐全再归档开发/审查窗口，总控继续使用。阶段验收是 G5，不能用几个已通过小任务代替整个阶段结论。

## 7. 当前还不能省略的确认

实际板卡/PCB、供电电平、引脚与手册对应关系；工具运行、目标器件支持及下载能力；首次板上操作；新接口和性能口径的冻结。相关项目仍待实验核实，文档准备不等于已验证。

Skill 暂不作为启动条件。先完成真实闭环，再根据重复遗漏和稳定自动步骤决定是否加入。
