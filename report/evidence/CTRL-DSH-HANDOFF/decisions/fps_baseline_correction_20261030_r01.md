## 1. 新事实（有原始 UART 行）
RunId `bringup_longrun_probe_20261029_r05`（2B 平台位流 `555a70c2…`、SW 预处理、真实 fixture）：

⇒ **真实单帧检测时间 = 47.287 s ⇒ 0.0211 fps**。

## 2. 根因（已定位到代码）
`xtimer_config.h` 的无括号宏 + `(uint64_t)` 强转优先级 ⇒ 计时有效分母变成 **1,333,333,374（4× 全局定时器）**，
导致应用把真实 47.3 s 报成 11.8 s。修复：分母 `S4D_MS_DIV=((uint64_t)(COUNTS_PER_SECOND))=333,333,343`，计数读 GT（noinline 一致读）。
证据：`S4-T34/s4d_time_basis_20261029_r01/ERRATUM_ROOT_CAUSE.md`（接任窗口产出）。

## 3. 影响与更正
1. **检测帧率**：0.0211 fps（47.287 s/帧），**不是** 0.085 fps；历史所有"11.8 s/帧 / 0.085 fps"作废（属同一 4× 口径错误）。
2. **2 fps 所需提升**：47.287 / 0.5 = **≈94.6×**（不是 23.6×）。外包任务（`DSH-20261029-006-task-fps-2fps-to-codex`）的基线按此更正。
3. **L0 剖析**：其"11.8 s @50 MHz 物理不可能"的观察正确（11.8 s 本就是错误数字）；按 47.287 s @50 MHz ⇒ ≈**2.36e9 拍/帧**，是冻结下界 616,778,290 拍的 **≈3.8×**，与"板级 lane 利用率 17.9%"一致。**L0 的三项冻结预算数（迭代/重读/写）仍有效**，但其"11.8 s 折算"的结论要按新基线重述。
4. **阶段4 长跑项**：r05 应用 RESULT 为 `exit=0 / within_judgement=1 / 40 轮 / 30.7 min 真实 / 零失败`，**按真实口径成立**；运行器 `W2_longrun` 仍记 `FAIL exit=1`，原因是其 `parse_result` 用 `json.loads` 解析裸十六进制 `box_*` 字段失败（工具缺陷，已在 `RESULT.md` 更正并修解析器）。**判读以应用 RESULT + 原始 UART 行 + 主机/应用比值 1.000 为准，运行器状态属工具缺陷**；证据不删除、不覆盖。
5. 上述不改变冻结件、不改判据；`ENABLE=0`；不主张 G3/G4/G5。
