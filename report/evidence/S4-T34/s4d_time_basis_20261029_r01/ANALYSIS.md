# 时间基座定因（2026-10-29 18:24–18:32）：`XTime_GetTime` 比全局定时器慢 4 倍

- RunId：`s4d_time_basis_20261029_r01`；窗口 18:24:55 → 18:32:10（UTC+8）
- 目的：判定"应用自报时间 ÷ 主机实测 ≈ 4"的来源（判据本身的基座问题）
- 结论：**已定因**——同一段等待内，主机与 Zynq 全局定时器一致，而 BSP 的 `XTime_GetTime` 只走 1/4。

## 1. 三方对照（同一段 DONE 等待）

| 计时源 | 读数 |
|---|---|
| 主机时间戳（UART 行 `wait_done_pre` 2.051 s → `done` 34.232 s） | **32.18 s** |
| 应用自报 `elapsed_ms`（内部用 `XTime_GetTime`） | **8.096 s** |
| 比值 | **3.975 ≈ 4** |
| Zynq 全局定时器直读（JTAG，`0xF8F00200/204`） | 2,199,355,488 counts / 7.46 s 主机 ⇒ 约 **295 MHz**（含 xsdb 启动开销，真值≈333 MHz，与下条一致） |
| BSP 常量 `COUNTS_PER_SECOND`（`xparameters.h: XPAR_CPU_CORE_CLOCK_FREQ_HZ 666666687` / 2） | **333,333,343** |

⇒ 全局定时器（333 MHz）与 BSP 常量（333.3 MHz）**一致**；不一致的是 `XTime_GetTime`：
它在这段 32.18 s 真实时间里只前进了 8.096 s × 333.3 MHz ≈ 2.70e9 counts
（等效计数器频率 ≈ **83 MHz**），即 **`XTime_GetTime` 的时基是全局定时器的 1/4**。

## 2. 影响（必须同步修正的口径）

1. **A 项"30 min 长跑"判据**：应用 `wall_ms ≥ 1,800,000` 实际 ≈ **2 h 真实时间**。若改用真实 30 min，
   按实测 ≈47.4 s/轮，仅约 **38 轮**；历史停住点（23/24/40 轮）≈18/19/32 min 真实时间。
2. **每帧延迟**：历史"11.8 s/帧"按真实时间 ≈ **47 s/帧**（2B 平台 FCLK0 设计值 50 MHz）。
3. **产品吞吐**：以真实 47 s/帧计，当前 2B 引擎远达不到 5–10 fps 检测；L0 剖析中"11.8 s"与"100 MHz"两个输入都要重算
   （2B BD 实际 `PCW_FPGA0_PERIPHERAL_FREQMHZ 50`）。
4. 本窗口同时复核了错误路径：缺权重时引擎按预期返回 `error_code=1`、`STATUS=0x0C05`、应用 FAIL→`exit=2`（与 2026-10-29 早期证据一致）。

## 3. 修复方向（PS-only，不需要重建位流）

- 把应用计时改为**直接读 Zynq 全局定时器**（`Xil_In32(0xF8F00200/0xF8F00204)`，64 位一致性读），
  分母用同一常量 333,333,343；或保留 `XTime_GetTime` 但按实测 4.0 缩放（不推荐，属掩盖）。
- 修完必须做**一次同窗口复核**：主机时间戳 vs 应用 `elapsed_ms`/`wall_ms` 比值 ≈ 1.00（允许 ±2%）。
- 修完再按**真实** 30 min 重跑 A 项；判据文本需同步改写并在 w4 STATE 留勘误，不得静默改判据。

## 4. 本窗口的其它事实

- 本次只预载了 RAW、**未预载权重**，所以引擎走错误路径（`done=2 st=0x0C05 error=1`），
  因此本窗口**只用于计时对照**，不作为任何功能/稳定性判据。
- 执行器已内置三条硬门禁（编程 PL 后禁 `rst -system`、装载命令静态自检、不用 `rst -system` 救场），
  本窗口全程未出现 `rst -system` 于编程 PL 之后；收窗后主机侧零残留。
- 未上板结论：`ENABLE=0`、未写 QSPI、未改线、未用 `-force`；不主张 G3/G4/G5。
